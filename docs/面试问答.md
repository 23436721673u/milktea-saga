# 奶茶物语 · 答辩 / 面试问答

> 写进简历前，请确认每个问题你都能不看稿讲清楚，并能在代码里指出对应位置。

## 1. 一句话介绍这个项目

一个奶茶店控制台点单系统，Java 21 + JDBC + MySQL 8，三层架构（entity / dao / service + 控制台表现层），5 张表。核心是"一单多杯"下单：用 JDBC 事务把写订单主表、写明细、扣库存、加积分四步做成原子操作，并用条件更新防止超卖。

## 2. 项目整体架构是怎样的？

- `Main`：只负责菜单和输入输出，捕获业务异常并显示中文提示。
- `service`：参数校验、业务规则、事务边界。例如 `OrderService.placeOrder` 决定什么时候开启、提交、回滚事务。
- `dao`：只写 SQL，全部使用 `PreparedStatement`。需要参与事务的方法接收外部传进来的 `Connection`。
- `entity`：和表一一对应的数据对象；`OrderItem.drinkName` 是只在 JOIN 查询时填充的展示字段。
- `util`：`DbUtil` 统一获取连接（配置可来自环境变量 / db.properties / 默认值）、`PasswordUtil` 做 SHA-256、`ConsoleUtil` 集中做输入兜底。

## 3. 下单结算是怎么做的？

1. 识别会员（手机号）或散客（输入 0）；未注册的手机号可以当场开卡。
2. 循环输入奶茶 ID 和杯数，加入购物车时就检查"库存 ≥ 本次杯数 + 购物车里已有杯数"。
3. 确认清单后调用 `placeOrder`：先合并同款、按数据库当前价格重建明细（单价快照）、再次校验库存。
4. 开启事务：INSERT 主表拿到订单号 → 批量 INSERT 明细 → 逐条条件扣库存 → 会员加积分 → COMMIT。
5. 任何一步失败就 ROLLBACK，界面提示"下单失败，已回滚"。

## 4. 事务在项目里用在哪？为什么必须用？

用在 `OrderService.placeOrder`。下单涉及 3 张表、4 类写操作。如果不用事务，假如写到第二条明细时数据库断开，会出现"订单写了一半、部分库存已扣、积分没加"的不一致状态。事务保证这几步要么全部成功，要么全部撤销。

实现要点：同一个 `Connection` 贯穿所有 SQL；`setAutoCommit(false)` 开始，`commit()` 提交，`catch` 里 `rollback()`，`finally` 里恢复 `autoCommit` 并关闭连接。DAO 方法签名带 `Connection` 参数就是为了让多个 DAO 共用同一个事务。

## 5. 如何防止库存超卖？

扣库存的 SQL 是：

```sql
UPDATE drink SET stock = stock - ? WHERE id = ? AND is_active = 1 AND stock >= ?
```

判断和扣减在一条 UPDATE 里完成，由 InnoDB 行锁保证原子性。两个店员同时卖最后几杯时，后执行的那条 UPDATE 因为 `stock >= ?` 不成立而影响 0 行，代码检测到影响行数 ≠ 1 就抛异常，整单回滚。

事务前也查了一次库存，那只是为了尽早给店员友好提示；真正的保证是这条条件更新。如果被追问更高并发的方案：可以用 `SELECT ... FOR UPDATE` 悲观锁、版本号乐观锁，或者用 Redis 预扣库存 + 消息队列异步落库。

## 6. 积分为什么用 `points = points + ?`？

如果先 SELECT 出积分、在 Java 里加完再 UPDATE 回去，两笔订单并发时会出现"后写覆盖先写"，丢失一次积分。让数据库原子累加就没有这个问题。积分规则是满 1 元加 1 分、向下取整（`setScale(0, RoundingMode.DOWN)`）。

## 7. 为什么订单明细要存 `unit_price`？

奶茶会改价。如果明细只存 `drink_id`，查历史订单时只能拿到现在的价格，账就对不上了。存下单时的单价快照，历史订单金额永远准确。

## 8. 为什么下架用软删除？

如果真的 DELETE 奶茶，外键约束会阻止删除；就算去掉外键强删，历史订单 JOIN 时也找不到奶茶名。软删除只把 `is_active` 置 0：商品列表和下单不再显示它，历史订单照样能查到名字和价格。

## 9. 多表 JOIN 用在哪？

- 订单明细：`order_item JOIN drink`，带出奶茶名。
- 销量榜：`order_item JOIN drink JOIN tea_order`，按奶茶 `GROUP BY` 求 `SUM(quantity)`，只统计本月已支付订单，`ORDER BY` 杯数倒序 `LIMIT 3`。
- 会员历史订单只查 `tea_order` 单表：会员信息已经在内存里，不需要 JOIN。

## 10. 怎么防 SQL 注入？密码怎么存？

所有 SQL 都用 `PreparedStatement` 的 `?` 占位符，参数只会被当作数据，`' OR '1'='1` 这类输入不会改变 SQL 结构。密码只存 SHA-256 摘要，登录时对输入做同样的摘要再比对；登录失败不区分"用户不存在"和"密码错误"，防止账号被枚举。如果被追问：SHA-256 没有加盐、计算太快，生产环境应换成 BCrypt / Argon2。

## 11. 金额为什么用 BigDecimal？

`double` 是二进制浮点数，`0.1 + 0.2 != 0.3`，累加金额会产生误差。数据库用 `DECIMAL`，Java 用 `BigDecimal`，加法用 `add`、乘法用 `multiply`、除法指定保留位数和舍入方式。

## 12. 开发中踩过的坑与注意点

- `order` 是 MySQL 保留字，订单表改名 `tea_order`。
- `rs.getLong("member_id")` 遇到 NULL 会返回 0，需要用 `rs.wasNull()` 区分散客。
- 用 `getTimestamp` 读 DATETIME，在 JVM 与数据库时区不一致时会偏移 8 小时，改为 `getObject(..., LocalDateTime.class)`。
- 同一款奶茶分两次加入购物车时，如果逐行校验库存，会漏掉"合计超出库存"，所以加购时累加已选杯数，下单前再合并同款。
- `new Scanner(System.in)` 在 Windows 命令行（GBK）里读中文会乱码，改为使用控制台自身的编码。

## 13. 如果继续迭代会做什么？

订单取消（回补库存、扣回积分，同样放在事务里）、积分兑换、连接池（HikariCP）、角色权限（RBAC），再升级成 Spring Boot + Vue3 的 Web 版。
